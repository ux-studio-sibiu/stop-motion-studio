Resize a picture's duration

A picture's width on the timeline is how long it stays on screen, and now that width can be dragged. Select a picture, grab the handle on its right edge and pull. It grows in whole ticks, a bubble says how long it is ("0.5 s"), and everything after it slides along. [ and ] do the same from the keyboard, one tick at a time. Each drag or key press is one undo step.

What was built

  • ProjectRepository.updateFrames(projectId, changes): changes frames' hold, transform or adjust in one transaction. 2 contract tests. Moving, zooming and brightening (steps 18–19) will use it too.
  • setHold(projectId, changes) in core/commands: one command for a whole resize, however many pictures it changed. 3 tests against storage.
  • ticksFromPx and resizeHolds in core/model/timing.ts. 4 tests.
  • A hold preview in the editor store (holdPreview, previewHolds, clearHoldPreview) and withHoldPreview(), which applies it to the frames. 5 tests.
  • src/studio/useResize.ts: the drag, the tap-through, Escape and the [ ] keys. The timeline gets a grip and a bubble on selected pictures.
  • useHistory().run now says whether a command was saved, so a failed resize can put the preview back.
  • e2e/resize.spec.ts (8 tests) and grip() / dragGrip() in the page object.

One drag, step by step

pointerdown on the grip   remember the selected pictures' lengths, capture the pointer
pointermove               delta = round(dx / px per tick); store.previewHolds(length + delta)
                          → the timeline redraws at the new widths; storage isn't touched
pointerup                 history.run(setHold([{ id, from, to }, …]))   one command
                          → saved; the store's preview entry goes once storage reports it back
Escape / pointercancel    store.clearHoldPreview(): back as it was, nothing saved

Decisions

While dragging, only the screen changes

Saving on every pointer move would write to IndexedDB dozens of times a second and fill the undo history with tiny steps. Instead the new lengths live in the editor store as a preview, and the timeline draws with them. Letting go runs one setHold command.

A preview entry is dropped once the saved frame has that length (in syncProject), so the width never flickers back to the old value while the save is on its way. If the save fails, the preview is cleared and the picture shows its saved length again.

Snapped to whole ticks

Lengths stay whole ticks, never less than 1, so every duration is a whole number of 1/fps. Changing the speed (step 16) then scales all of them evenly. A drag of dx pixels is round(dx / px per tick) ticks, so the edge jumps to the nearest tick mark.

Several pictures: the same amount each

With several selected, dragging any of their grips changes all of them by the same number of ticks. Shortening keeps each one at least 1 tick: a 1-tick and a 3-tick picture shortened by two become 1 and 1, and only the one that changed is saved.

The grip shows on selected pictures only

At the default zoom a picture is 20 px wide. A 24 px grip on every picture would cover them all, and clicking to select would start resizes. So:

  • You select first, then drag.
  • The grip's hit area is 24 px, finger-sized, but reaches only 4 px into the next picture. The first version reached 12 px, which covered a narrow neighbour so it couldn't be clicked; the multi-select Playwright test caught it.
  • A tap on the grip without moving (under 4 px) counts as a click on the picture, with Shift or Ctrl. A narrow selected picture is mostly grip, and can still be Ctrl+clicked out of the selection.

The grip uses pointer events with setPointerCapture, so the drag keeps following the pointer anywhere on the page. touch-action: none makes a finger drag resize instead of scrolling the timeline. It's separate from the reorder drag coming in step 14.

The capture marker became a dot

Step 12's red "next picture goes here" bar ran down the same right edge as the grip and hid it. The marker is now a red dot just above that edge.

[ and ] pressed quickly

Each press is a command, and builds on the length on screen: the preview, if the previous press isn't saved yet. Three quick presses give +3 ticks, not +1 three times, and each undoes on its own.

A preview isn't a selector

The timeline doesn't read the frames with the preview applied through a store selector. Such a selector builds new frame objects every time it runs, and React's useSyncExternalStore would see a "new" value every render and re-render forever. Instead the timeline reads frames and preview separately and combines them with withHoldPreview() in a useMemo. Frames without a preview stay the same objects, and a test checks that.

A test bug from step 12, fixed

The late-first-frame camera test (step 09, made deterministic in step 12) hung about 1 run in 5 at page.goto. Chrome holds back the page's "load" event while a <video> waits for its first frame. In this test the frame only comes when the test sends it, after loading, so each was waiting for the other. The test now loads with waitUntil: "domcontentloaded", and passed 10 runs in a row on its own.

Watch out

  • No auto-scroll while dragging near the timeline's edge. A very long drag needs zooming out first. Auto-scroll comes with reordering (step 14), which needs it too.
  • Overlays (step 24) stay at their times when a picture gets longer; only pictures slide. That step must show it clearly.
  • The grip is for pointers. Screen reader and keyboard users have [ and ]; the grip itself is aria-hidden.

  • Take a few pictures, click one, drag its right handle: the bubble counts up in steps ("0.25 s", "0.38 s", "0.5 s"), and the pictures after it move along.
