End-to-end tests with Playwright

The studio is now tested the way a child uses it: in a real browser, with a webcam (a fake one playing a generated video), real IndexedDB, real clicks and real reloads. Seven tests cover the camera, saving, reloading and the "missing project" page, in Chromium and WebKit. This page explains Playwright from scratch, because every later step adds to these tests.

What was built

  • @playwright/test 1.65, and its Chromium and WebKit browsers (downloaded once per machine into %LOCALAPPDATA%\ms-playwright).
  • playwright.config.ts: builds and serves the app on port 3200, two browser projects, the fake-camera flags, traces on failure.
  • e2e/fake-camera.ts: writes the webcam video (e2e/.generated/fake-camera.y4m, ignored by git) before the tests start.
  • e2e/fixtures.ts: a studio fixture with a Studio page object (open, cameraOn, takePictures, …) and a script camera for browsers without a fake device.
  • e2e/camera.spec.ts: camera on → live picture; off and leaving → the track really stops; blocked → the blocked message.
  • e2e/persistence.spec.ts: 3 pictures survive a reload; a new project starts empty; Back returns to the same project; an unknown id shows the friendly page.
  • Scripts test:e2e, test:e2e:ui, test:e2e:report; report and result folders in .gitignore; an ESLint override for e2e/.

What an end-to-end test is

A unit test (Vitest) calls one function and checks what it returns. An end-to-end test starts the whole app, opens it in a browser and acts like a person: click this, wait for that, reload. It checks what appears on screen. Same idea, tested both ways:

await repository.insertFrames(id, {...});

That's why both stay: many fast unit tests for the logic, a few end-to-end tests for the flows that matter.

How Playwright drives a browser

Playwright ships its own builds of Chromium, Firefox and WebKit. The test runner starts one as a separate process and talks to it over its automation protocol (Chrome DevTools Protocol for Chromium, a similar one for WebKit), the same channel DevTools uses. Every action (click, fill, reload) is a message to the browser; the page itself runs exactly as it would for a person.

browser   one browser process, started once per worker
  └─ context   like a fresh browser profile: its own cookies, localStorage and IndexedDB
       └─ page   one tab

Every test gets a new context. That's why each test starts with an empty database: a test can't see another test's pictures, and tests can run in parallel and in any order. Creating a context takes milliseconds, unlike starting a browser.

The test runner

e2e/persistence.spec.ts

import { expect, test } from "./fixtures";

test("pictures survive a reload", async ({ studio, page }) => {
  await studio.open();
  await studio.cameraOn();
  await studio.takePictures(3);
  await page.reload();
  await expect(studio.pictures()).toHaveCount(3);
});
  • test(name, fn) defines a test, like Vitest's it. test.describe groups, test.beforeEach runs setup, test.skip(condition, reason) skips with a reason shown in the report.
  • Fixtures are the arguments of the test function: { page }, { context }, { browser } are built in. Playwright creates each one before the test and cleans it up after, only if the test asks for it.
  • Custom fixtures extend that list. e2e/fixtures.ts adds studio: it installs the script camera when the project needs one, then hands the test a Studio object. Tests import test from ./fixtures instead of from Playwright.
  • Options are fixtures that projects set: fakeCamera: "device" | "script" is set per browser in the config, and the studio fixture reads it.

The page object

Studio names the things a test does, in the studio's own words: open(), cameraOn(), takePictures(3), pictures(). Tests read like the flow they check, and when a button's label changes, only fixtures.ts changes, not every test.

Locators and auto-waiting

A locator describes how to find something, not the element itself: page.getByRole("button", { name: "Take a picture" }). It's looked up again every time it's used, so it's never stale after a re-render.

  • Find things the way people do. getByRole (a button, a link, a heading, by its accessible name), getByLabel, getByText. Not CSS classes: classes change for styling reasons and say nothing about what the user sees. If a test can't find a button by its name, a screen reader can't either, so these tests double as a basic accessibility check. Two places still use selectors (video, .picture-count), where there's no role to find them by.
  • Actions wait. Before click(), Playwright waits until the element is attached, visible, stable (not animating), enabled and not covered by something else. No "wait 500 ms" needed.
  • Web-first assertions retry. await expect(locator).toHaveCount(3) checks again and again until it's true or 5 seconds pass. That's how a test waits for a capture to be saved and shown without guessing how long it takes. expect.poll(() => value) does the same for any value, like a video's width.
  • Never waitForTimeout. A fixed sleep is either too short on a slow machine (flaky) or too long everywhere (slow).
Building this step hit exactly the trap auto-waiting can't cover: if (await button.isVisible()) checks once, right now. Straight after the page loaded, neither "Turn on camera" nor the live camera was on screen yet, so the check said "not visible", skipped the click and the camera never started. The fix waits for one of the two first: await expect(turnOn.or(live)).toBeVisible(), then decides.

The config, line by line

playwright.config.ts

testDir: "e2e",                          // where the *.spec.ts files are
globalSetup: "./e2e/fake-camera.ts",     // runs once before any browser: writes the webcam video
fullyParallel: true,                     // tests run side by side in several workers
forbidOnly: !!process.env.CI,            // a forgotten test.only fails on CI
retries: process.env.CI ? 1 : 0,
reporter: [["list"], ["html", { open: "never" }]],

webServer: {
  command: "npm run build && npx serve out -l 3200 --no-port-switching",
  url: "http://localhost:3200",          // Playwright waits until this answers
  reuseExistingServer: !process.env.CI,  // locally, a server already on 3200 is reused
},

use: {
  baseURL: "http://localhost:3200",      // page.goto("/studio") means this server
  trace: "retain-on-failure",            // a failed test keeps a trace to replay
},

projects: [
  { name: "chromium", use: { ...devices["Desktop Chrome"], permissions: ["camera"], fakeCamera: "device",
      launchOptions: { args: [ "--use-fake-ui-for-media-stream", "--use-fake-device-for-media-stream",
                               "--use-file-for-fake-video-capture=…/fake-camera.y4m" ] } } },
  { name: "webkit", use: { ...devices["Desktop Safari"], fakeCamera: "script" }, grepInvert: /@real-camera/ },
],
  • The production build, not next dev. It's what ships, it has no dev overlay, and it doesn't run React Strict Mode's double effects, which would make tests behave differently from real use. Port 3200 keeps it away from your next dev on 3000.
  • Projects are "the same tests, with these settings". Every test runs once per project unless filtered: grepInvert: /@real-camera/ leaves out tests with that tag in their name in WebKit.
  • devices[...] sets a viewport, user agent and scale factor that match a typical desktop.

The fake camera

Chromium has three switches for exactly this:

  • --use-fake-ui-for-media-stream: answers the "allow camera?" prompt with yes.
  • --use-fake-device-for-media-stream: replaces real webcams with a fake device (without a file it shows a test pattern).
  • --use-file-for-fake-video-capture=file.y4m: the fake device plays this video, on a loop.

permissions: ["camera"] also grants the permission at the browser level, so the studio sees "already allowed" and starts the camera by itself.

The video format. Y4M (YUV4MPEG2) is about the simplest video file there is: one text line (YUV4MPEG2 W320 H240 F15:1 Ip A1:1 C420jpeg: size, 15 frames per second, square pixels, 4:2:0 colour), then each frame as the word FRAME, a newline, and raw pixels. Pixels are YUV: a full-size plane of brightness (Y), then two quarter-size planes of colour (U and V), one byte per value. e2e/fake-camera.ts writes 30 frames of a white square sliding across a green field, 320×240 (4:3, so the 16:9 crop is exercised too). That's 3.4 MB of raw video: too big for git, generated in milliseconds.

WebKit has no file-backed fake camera, so its project uses a script camera: before the page's own code runs, addInitScript replaces navigator.mediaDevices with one whose getUserMedia returns a canvas stream. Playwright's WebKit build for Windows turned out to have no media streams at all (no navigator.mediaDevices, no canvas.captureStream), so no camera can be faked there: cameraOn() checks for it and skips the test, with the reason in the report. On macOS or Linux (for example a CI runner) those tests run. The tests that don't need a camera run in WebKit everywhere.

Decisions

  • Vitest stays for logic; Playwright covers the handful of flows a child goes through.
  • A page object instead of raw locators in every test, so the UI's wording lives in one place.
  • Tags in test names (@real-camera) choose which browsers run what, instead of separate folders.
  • Skip with a reason, never silently pass. Where a browser can't fake a camera, the test says "skipped: no media streams", so a green run never hides untested flows.
  • Assert counts and states, not pixels. The fake video moves, so two captures never match pixel for pixel. Tests check "3 pictures", "the thumbnail is 160 px wide", "the track has ended". Pixel checks come with the renderer (step 15), on still images.
  • One lint override: the React hooks rule mistakes Playwright's fixture function use() for React's use() hook, so it's off for e2e/.

Watch out

  • A stale server. Locally, a server already on port 3200 is reused, and it serves whatever is in out/. If tests behave like old code, stop that server (or run npm run build) and run again.
  • Browsers are per machine. After cloning, or after a Playwright upgrade: npx playwright install chromium webkit.
  • One check is not a wait. isVisible(), count() and textContent() answer once. To wait, use expect(...) or expect.poll(...).
  • Captures are one at a time. takePictures() waits for each thumbnail before the next press, because presses during a save are ignored on purpose (step 05).
  • Tests are independent. Never rely on another test's data or order; make what you need inside the test.
