Brightness and contrast

A cloud passes, a lamp gets moved, and one shot comes out darker than the rest. Now a child can fix it. The Picture tab has two sliders, Brightness and Contrast (50% to 150%), and Reset to go back to the photo as it was taken. With several pictures selected, they change them all, in one undo step. The photo itself is never changed; the values are applied when drawing. The stage and the timeline thumbnails show them.

What was built

  • clampAdjust (50-150%, whole percents) and sameAdjust in core/model/project.ts. 2 tests.
  • setAdjusts(projectId, changes, label) in core/commands: one command for a slider drag or a Reset, however many pictures it changes. 2 tests against storage.
  • src/core/render/adjust.ts, the fallback for browsers without ctx.filter:
    • adjustPixels and adjustTable, the pixel loop. 4 tests.
    • canvasFilterWorks.
    • adjustedCopy: an adjusted copy of a picture, kept until the values change.
  • drawFrame uses the canvas filter where there is one, and the adjusted copy where there isn't. 2 pixel tests: the two ways match within 2 levels, and the values come out exactly.
  • An adjust preview in the store (adjustPreview, previewAdjusts, clearAdjustPreview, withAdjustPreview), like the move preview. 1 test.
  • useShownFrames() in store/useEditor.ts: the frames with every unsaved change (moves and adjustments). The stage picture, see-through and the stage editor now all use it.
  • src/studio/AdjustControls.tsx: the sliders and Reset. Wired through useStudioCommands (adjustPictures).
  • Timeline thumbnails get the same values as a CSS filter (TimelineFrame.tsx).
  • 2 end-to-end tests in e2e/picture.spec.ts.
Changed after review: a "Use for all pictures" button was dropped; selecting several pictures does the same. "Normal" is now called "Reset", like the position's reset.

Decisions

  • Non-destructive. The frame stores two numbers; the renderer applies them, so export (steps 25-27) will show what the stage shows.
  • Like moving a picture. While a slider moves, the stage shows a preview and nothing is saved. Letting go saves one step. A run of arrow presses is saved once it stops (the same 600 ms as nudges), so it's one undo. With several pictures selected, the slider changes them all.
  • The fallback follows CSS. It applies brightness() then contrast(), each kept between black and white, so the pictures look the same in every browser. The pixel test checks it against the real canvas filter.
  • The fallback isn't skipped during drags. The roadmap warned it could be slow at 1080p. Pictures here are at the project's size (1280 × 720), and each adjusted copy is computed once per picture and value, so one slider step costs one pass over the picture. If it shows up as slow on an older iPad, the step to take is to skip it while the slider moves.
  • Range 50-150%. That's enough to rescue a dark or flat shot without making a white or black page.

Watch out

  • canvasFilterWorks checks the context's prototype, not the context: setting an unknown property on the context would just store it, and it would read back fine. The Node test's fake context was given a prototype with filter to match.
  • In the fallback, the extra style (see-through's outline look) is left out. Only browsers without ctx.filter see that.
  • Not checked here: a real Safari without ctx.filter. WebKit's camera tests don't run on Windows, and this machine's WebKit has the filter. The pixel test runs the fallback in Chromium instead.

Check it

  • Make a picture brighter, undo, redo. Reload: it's still brighter, on the stage and in its thumbnail.
  • Select several pictures, move a slider, then one undo: they all go back.
