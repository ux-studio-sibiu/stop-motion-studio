How IndexedDB and Dexie work

IndexedDB is a database built into every browser, private to the site that created it (here, the studio's origin). It stores JavaScript objects, including Blobs, directly; no conversion to text. Data is grouped in object stores (tables) with a primary key, and indexes on other fields make lookups like "all frames of this project" fast. All work happens in transactions: either everything in a transaction is written, or nothing is.

The raw IndexedDB API is event-based and wordy. Dexie wraps it in promises and a small query language: db.frames.where("projectId").equals(id).toArray(). db.transaction("rw", tables, async () => { ... }) runs a function in one transaction; if anything inside throws, Dexie aborts it and every write in it is undone. A version is the database's layout; when the app ships a new version, Dexie upgrades each browser's existing database the first time it opens.

Decisions

The studio depends on an interface, not on Dexie

ProjectRepository lives in core/ and says what storage can do, in the app's own words. createDexieRepository in adapters/ is one way to do it. The editor, the store and the commands (step 11) will only see the interface, so a cloud backend later is a second implementation, not a rewrite.

A contract test, written once

The tests describe the interface, not Dexie: "deleting a project removes its pictures and nothing else", "a frame of another project is refused and nothing is saved". They take a function that makes a fresh repository, so a future implementation reuses all of them by calling describeRepositoryContract("Supabase", ...). Only things that are true of Dexie alone (the schema, version numbers) are tested separately.

Changes that touch several tables are one transaction

insertFrames writes images, thumbnails, frames and the project's new order together; deleteProject removes from all four tables together. If the disk is full halfway through, nothing is half-saved: there's never a frame whose picture is missing, or a picture no frame can reach. A test forces a failure on the last write and checks that the earlier writes were undone.

Thumbnails in their own table

listThumbs(projectId) loads a project's small pictures without reading a single full photo. Opening a project with 300 pictures loads about 300 KB of thumbnails instead of 50 MB of photos. Full pictures are read one at a time with getImage when playback or export needs them.

Index only what's searched

Every index costs space and slows writes. updatedAt sorts the project list, projectId finds a project's frames, images and thumbs. Nothing else is indexed, though every field is still stored.

The order stays in project.frameIds

Frames are stored unordered; loadProject returns them as found, and the project's frameIds list is the order (step 02). Inserting at a position rewrites one list, not every frame.

Opened on first use, never at import

studioDb() creates the database the first time the app asks for it. next build renders pages in Node, where there is no IndexedDB; opening the database when the file is imported would crash the build. Tests don't use studioDb() at all: each one opens its own database with a random name and deletes it afterwards.

The repository sets updatedAt

Every change through the repository stamps the project with the time, so the projects page (step 09) can list the most recently touched first without every caller remembering to do it. The clock is a parameter, so tests set exact times.

How the tests run without a browser

import "fake-indexeddb/auto" at the top of the test file installs a complete IndexedDB written in JavaScript as Node's global indexedDB. Dexie can't tell the difference, so the real repository code runs against it. It follows the IndexedDB spec closely (including transactions and Blob storage), but it isn't a browser: storage quotas, eviction and browser quirks are not tested here. That's what the Playwright tests in step 08 add.

Watch out

  • Never edit version(1) once it has shipped. A changed layout goes in version(2) with an upgrade() that moves the old data. Until the app ships (step 33), deleting the dev database is fine: DevTools > Application > IndexedDB > stop-motion-studio > Delete database.
  • No await on non-Dexie work inside a transaction. IndexedDB closes a transaction as soon as it's idle; awaiting a fetch or a toBlob in the middle ends it, and the next write fails with TransactionInactiveError. Encode pictures first, then open the transaction.
  • Every table a transaction touches must be listed in db.transaction(...), or Dexie throws.
  • Blobs are copied in. After insertFrames, the stored Blob is the browser's own copy; changing the original does nothing to it.
  • Storage can run out. Writes can fail with QuotaExceededError; step 20 turns that into a friendly message. For now the error reaches the caller.
