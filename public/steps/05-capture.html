Build steps · Step 05 of 33 · Part 2 Capture

Capture to an in-memory timeline

The big red button (or Space) takes a picture: the live camera frame is cropped to the project's 16:9 shape, resized to 1280×720, saved as a JPEG with a small thumbnail, and added to the end of the animation. The timeline shows the thumbnails, numbered, and a tap selects one. Nothing is saved yet: leaving the studio drops the pictures until step 07.

What was built

  • src/core/render/fit.ts: coverCrop(), the "fill without stretching" maths (CSS object-fit: cover), with 5 tests. The renderer will reuse it.
  • src/adapters/camera/capture.ts: captureFrame(video, size) returns { image, thumb, width, height }: a 1280×720 JPEG at quality 0.9 and a 160×90 thumbnail at 0.8.
  • src/adapters/images/imageCache.ts now also hands out object URLs (url(imageId)), made once per image and revoked when the image is replaced, deleted or cleared. 2 new tests.
  • src/studio/media.ts: the open project's two caches, images and thumbs, and clearMedia().
  • src/studio/useCapture.ts: capture() (take, cache, add a frame) and the Space shortcut.
  • src/studio/Timeline.tsx: the thumbnail strip with picture numbers, selection, and a "next picture goes here" slot that stays in view.
  • Capture button enabled when the camera is live, a picture counter under it ("3 pictures", read out by screen readers), and a short white flash on the stage (off with reduced motion).
  • CameraView hands its <video> to the studio through an onVideo callback.

What happens on a press

press / Space
  → captureFrame(video, project)      draw the current video frame, cover-cropped, at 1280×720
                                      draw that picture again at 160×90 for the thumbnail
                                      encode both as JPEG (toBlob)
  → images.put(id, image)             full picture: in memory (IndexedDB in step 07)
    thumbs.put(id, thumb)             thumbnail: in memory
  → insertFrames([createFrame(...)])  the store gets a new frame pointing at the image id
  → the Timeline re-renders           its <img> src is thumbs.url(id)

Decisions

Crop and resize at capture time

Webcams deliver all sorts of shapes and sizes: 640×480, 1920×1080, 4K, portrait on phones. Every picture is turned into the project's shape and working size the moment it's taken. Storage stays small and predictable (a 1280×720 JPEG is roughly 100-200 KB), and everything after this step (timeline, playback, export) can assume every picture is the same size.

The crop is the same one the preview shows

The live <video> uses CSS object-fit: cover (step 03); coverCrop() computes exactly that rectangle for the canvas. So the picture contains what the child saw, no more and no less. With a 4:3 camera, a strip at the top and bottom is cut off in both.

src/core/render/fit.ts

coverCrop(640, 480, 1280, 720)   // → { x: 0, y: 60, width: 640, height: 360 }

The thumbnail is made from the picture, not the video

It's drawn from the cropped 1280×720 canvas, so it can never show a slightly different crop or a frame a few milliseconds later. It's stored separately so the timeline never has to load or decode the full pictures.

The cache owns the object URLs

An <img> can only show a Blob through a blob: URL made with URL.createObjectURL, and each one keeps its Blob in memory until URL.revokeObjectURL. The roadmap planned a useBlobUrl hook per thumbnail; making the URL inside a component turned out fragile (React may render twice, and revoking in a cleanup can blank an image that's still on screen). Instead the cache makes one URL per image, hands the same one to every component, and revokes it only when the image itself goes away. Components just read thumbs.url(id).

One picture at a time

The current video frame is drawn the instant the button is pressed; encoding the JPEGs takes a moment after that. Presses during that moment are ignored, so a double tap gives one picture, and pictures always arrive in the order they were taken. Normally the gap is well under a tenth of a second.

Space captures, unless something else wants it

Space anywhere in the studio takes a picture. It's ignored while typing (inputs, text areas, editable text) and when a button or link has focus, because Space already presses the focused button; capturing as well would do two things at once. Held-down Space (key repeat) doesn't fire a burst.

The studio owns the video element

CameraView still sets the stream on its own <video>, and passes the element up with onVideo(element); the studio keeps it in a ref for capturing. Passing a ref object down and having the child write into it is what the React compiler's lint rule rejects ("This value cannot be modified"), and a callback keeps who-owns-what clear.

Watch out

  • videoWidth is 0 until the first frame arrives. captureFrame refuses then (the press is simply ignored, with a console warning), and the button is only enabled once the camera is live. Since step 09: and once the first frame has actually arrived; before that, a press was silently ignored.
  • toBlob can return null (out of memory, a canvas that's too big). It's turned into an error, not a missing picture.
  • Canvas memory. The two canvases are shrunk to 0×0 after encoding; Safari otherwise keeps their pixels around until garbage collection.
  • Leaving the project changes the plan mid-capture. If the project changes while a picture is encoding, the picture is dropped instead of landing in the wrong project.
  • Never revoke a URL that's on screen. Only the cache revokes, and only when the image leaves it: on replace, delete, or clearMedia() when leaving the studio.
  • next/image can't handle blob: URLs, so the thumbnails are plain <img> with the lint rule switched off on that one line.

Check it

npm test
npm run dev
  • Turn on the camera, press the red button: a flash, a thumbnail at the end of the timeline numbered 1, "1 picture" under the button.
  • Press Space a few times (click on the stage first, so no button has focus): more pictures. With focus on "Camera off", Space toggles the camera and takes no picture.
  • Take 10 pictures: the timeline scrolls so the "next picture" slot stays in view.
  • Tap a thumbnail: it gets a blue outline.
  • With a 4:3 webcam, compare a thumbnail with the live view: same crop.
  • DevTools > Memory while capturing 20 pictures: memory grows by the JPEGs only (a few MB), not by a canvas per picture.
Checked while building, on the production build with a fake 4:3 camera (red band at the top, blue at the bottom, green in between): presses and Space add frames and the counter follows; presses while a picture is encoding are ignored; Space on a focused button takes no picture; the thumbnail is 160×90 JPEG and its top and bottom rows are green, so exactly the 4:3 → 16:9 crop was taken; selection outlines the tapped thumbnail; leaving the studio revokes the thumbnail URLs. Not checked: the auto-scroll (the preview window was hidden, so it had no width), a real webcam, a tablet.
