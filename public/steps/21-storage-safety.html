Storage safety

Photos take space, and a device fills up. This step makes sure the studio never wastes space and never loses work without saying so:

  • Deleted pictures' photos are cleaned up once no undo can bring them back: when the animation is left, or opened again.
  • A full device gets a message ("There's no room left on this device. That wasn't saved…") instead of a picture that silently isn't there.
  • Past 80% full, the studio warns, and so does the storage section on the projects page. Each animation's card says how much space it takes, so a child can see what to delete.

What was built

  • Two repository methods, held to the contract (4 tests):
    • removeUnusedImages(projectId) deletes the photos and thumbnails no frame uses, in one transaction. A photo shared by duplicates stays while any frame uses it. Other animations are never touched.
    • projectSizes(): the bytes each animation's photos take.
  • src/adapters/storage/projectSession.ts: when the clean-up may run, with Web Locks across tabs. 4 tests, against Node's own Web Locks.
  • src/adapters/storage/storageFull.ts: isStorageFull(error) recognises the browser's quota error, also when Dexie has wrapped it. 2 tests.
  • A storage notice in the store (storageNotice: full, almost full or none). 1 test.
  • useHistory shows "full" when any save, undo or redo fails for lack of space.
  • useStorageWatch checks the browser's estimate when the studio opens and after each picture.
  • StorageNotice.tsx: the message at the top of the studio.
  • useProject opens the session, so the clean-up runs on opening and leaving an animation.
  • On the projects page, each card shows its size (ProjectCard, useProjects), and StorageMeter warns past 80% (ALMOST_FULL in storageInfo.ts).
  • e2e/storage.spec.ts (3 tests).

Decisions

  • The clean-up never runs while an undo could still need a photo. Each studio holds a shared Web Lock on the animation it has open, and the clean-up only runs when it can take that lock alone. This tab's history is empty when the animation opens, and gone once it's left. If another tab has the same animation open, with its own undo history, nothing is deleted.
  • Without Web Locks, never clean up. Keeping a few photos too many is safe; deleting one an undo still needs isn't.
  • One message, two levels. "Full" (a save failed) is an alert, and an "almost full" estimate never replaces it. "Almost full" shows once per visit to the studio.
  • Nothing is half-saved. Every write is already one transaction (step 07), so a full disk leaves the animation as it was. The message says the change wasn't saved.

Watch out

  • Duplicates share their photo, so the clean-up looks for photos no frame uses, not photos of deleted frames. A contract test covers it.
  • Browsers only estimate how much space is used and allowed. The 80% warning is a hint, not a promise.
  • Next adds its own empty role="alert" element (it announces route changes). Tests pick the studio's alert by its text.

Check it

  • Delete pictures, go back to all projects, open the animation again: the photos are gone from storage, and the card's size drops.
  • In a test, make every write fail as a full disk does: the message shows, and the timeline is unchanged.
