Decisions

The list watches storage, like the studio does

watchProjects reports the list now and after every create, rename, capture or delete, from this tab or another. Deleting doesn't remove a card by hand; it deletes in storage, and the list updates. Same rule as step 07: storage is the truth, the screen follows it.

Covers load before the list shows

Each card shows its first picture's thumbnail, found with getCover(). They're loaded into a cover cache (the same ImageCache as the studio's thumbnails, which owns and revokes the object URLs) before the list updates, so no card ever appears without its picture and then pops one in. The cache is keyed by image id, so moving a different picture to the front gives the card a new cover.

Rename in place

The pencil turns the name into a text field, already selected. Enter or clicking away saves, Escape cancels. Whatever is typed goes through cleanName(): extra spaces go, a very long name is cut to 60 characters, and an empty one becomes "My animation" rather than a card with no name. Renaming counts as a change, so the animation moves to the top of the list.

Delete is the one thing that asks

Everything inside the studio will be undoable (step 11), but a deleted project can't come back. So delete opens a modal dialog with the picture and the name: Delete "Dino walk"? Its 12 pictures will be gone for good. This can't be undone. Keep it is focused, so Enter or a quick tap does nothing harmful; Delete is the red one. Escape also means "keep it". The project, its frames, photos and thumbnails go in one transaction (step 06).

A native <dialog> opened with showModal() does the hard parts: it keeps keyboard focus inside, makes the page behind inert, closes on Escape, and is announced as a dialog.

Asking the browser to keep the data

By default browser storage is "best effort": if the disk runs low, the browser may clear it. navigator.storage.persist() asks for "persistent" storage, which only the user can clear. It's asked when a project is created, a moment the child cares about, and never waited for: Chrome usually decides silently, Firefox may show a prompt, Safari often says no. The meter says which it is: "The browser has promised to keep your animations", or a gentle note that it may clear them, pointing at project backup (step 26).

The meter says "about"

navigator.storage.estimate() gives a usage and a quota, but both are estimates (browsers pad them to avoid leaking what other sites store). The meter says "Using 104 KB of about 10 GB on this device" and hides itself entirely when the browser can't tell. Warnings when it gets full come in step 20.

Two ways to start a project, one function

"New animation" and opening /studio without an id both call createSavedProject(), so both save the project and ask for persistent storage the same way.

A bug from step 05, found here

Taking screenshots of this page, a script pressed the capture button straight after the camera came on, and no picture appeared. The console said "The camera picture isn't ready yet." The capture button turned on as soon as the camera stream started, but some cameras take a moment longer to send their first frame; a press in that gap was silently ignored. A child would just see the button not work.

  1. A failing test first, as the repo's CLAUDE.md asks: camera.spec.ts › "the capture button waits for the camera's first picture" uses a camera whose first frame arrives after 1.5 seconds, and expects the button to be off until then. It failed: Expected: disabled, Received: enabled.
  2. The fix: CameraView only hands the video to the studio once it has a frame (loadeddata, with videoWidth > 0), and the capture button is enabled only then. The test passes.

Watch out

  • WebKit and parallel runs. With more tests, Playwright's WebKit on Windows started crashing now and then when about ten copies ran at once ("Target page, context or browser has been closed"), passing on the next run. The WebKit project now runs at most two at a time (workers: 2 in its project); three full runs in a row were clean.
  • persist() can prompt. Only call it where a person just did something (creating a project), never on page load or repeatedly. To show the state, use isStoragePersistent(), which never asks.
  • Long names on desktop cards are cut with "…" next to the two buttons; the full name shows in the rename field and on phones.
  • The list is per browser. Animations made in another browser or on another computer don't appear (the "isn't here" page from step 07 explains that).
