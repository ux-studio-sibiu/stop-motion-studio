Commands and undo/redo

Every change to an animation now goes through a command: an object that knows how to do the change and how to reverse it. A history of commands gives undo and redo. The first two commands are taking a picture and deleting pictures, so a child can delete a picture with the Delete key or the bin button, and get it back with Ctrl + Z or the undo arrow. All later edits (duplicate, resize, reorder, move, brighten) plug into the same history.

What was built

  • src/core/commands/, plain TypeScript:
    • command.ts: the Command type: label, do(repository), undo(repository), and an optional "select these afterwards".
    • history.ts: createHistory(repository or a function returning it, limit = 100) with run, undo, redo, state() (can undo / redo, and their labels) and subscribe. 10 tests.
    • frameCommands.ts: deleteFrames(projectId, ids) and addFrames(projectId, insert) (a capture).
  • ProjectRepository gains removeFrames() (takes frames out, keeps their photos, says where each one stood) and restoreFrames() (puts them back there). 4 contract tests.
  • core/model/order.ts: removeFromOrder, restoreToOrder and neighbourAfterDelete. 7 tests.
  • src/adapters/storage/frameCommands.test.ts: the commands against real (in-memory) IndexedDB, do → undo → redo. 7 tests.
  • src/studio/useHistory.ts: one history per open project, the undo and redo buttons, and the keyboard shortcuts. Capturing (useCapture) now runs addFrames through it.
  • The timeline gets a "Delete picture" button, and Delete / Backspace on the selected picture.
  • e2e/history.spec.ts (5 tests), and undoButton, redoButton, deleteButton and order() in the page object.

How a command works

history.run(deleteFrames(projectId, ["b", "d"]))
  do():   repository.removeFrames  → remembers [{ frame b, index 1 }, { frame d, index 3 }]
undo()
  undo(): repository.restoreFrames → b back at 1, d back at 3, both selected
redo()
  do() again

Decisions

Commands keep just enough to reverse themselves

A delete remembers the frames it took out and where each one stood, nothing more. It doesn't copy the whole project before and after. Restoring inserts them in ascending index order, which rebuilds the old order exactly; if the animation got shorter meanwhile, a picture goes to the end at most. A redo simply runs do() again.

Deleting a picture never deletes its photo

removeFrames deletes the frame and its place in the order, and leaves the photo and thumbnail in storage. That's what makes undo always possible, even many steps later, and it keeps the thumbnail in memory, so a restored picture shows up straight away. Photos no frame uses any more are cleaned up in step 21 (only once nothing in history can bring them back).

One command, one transaction

Each do() and undo() is a single repository call, and each of those is one Dexie transaction over the projects and frames tables. A delete either happens fully (frames gone and order updated) or not at all. The rollback test from step 06 still covers it.

Taking a picture is a command too

The roadmap only asked for delete, but a child who presses undo expects the picture they just took to go. addFrames saves the photo the first time, and after that undo and redo only move the frame in and out. It lets go of the photo's Blobs after the first save, so a hundred captures in the history don't hold a hundred photos in memory.

History is per open project, in memory

A new history starts when a project opens; leaving the studio or reloading starts empty again, and the pictures stay as they were saved. It keeps the last 100 commands; older ones drop off. A new command clears redo, as in every editor.

One at a time

Commands run in a queue: pressing Ctrl + Z three times quickly undoes three commands in order, never two at once against the same data. A command that fails isn't recorded. One whose undo or redo fails stays where it was, so the next press can try again.

Delete moves the selection straight away

Storage is still the source of truth (step 07): the timeline changes when the save comes back. But the selection moves to the next picture immediately, so pressing Delete three times quickly deletes three pictures. The first Playwright run caught this. Without it, the second press deleted the same, not yet vanished, picture again, and history recorded a step that did nothing. Deleting pictures that are already gone now fails instead of being recorded. Undo selects the pictures it brought back.

Shortcuts

  • Ctrl + Z (Cmd + Z on a Mac) undoes.
  • Shift + Ctrl + Z or Ctrl + Y redoes.
  • Delete or Backspace on the timeline deletes the selected picture.

None of them act while typing in a text field, where the field's own undo wins. Hovering the undo button says what it will undo ("Undo: Delete picture").

Watch out

  • Every edit is a command from now on. Writing to the repository directly from the UI skips history, and undo then jumps over that change. Opening and repairing a project (useProject) are the exceptions: they aren't edits.
  • do() runs again for redo. A command must work a second time after its undo: addFrames restores the frame on redo instead of saving the photo again.
  • Two tabs on the same project each have their own history. Undo in one tab reverses only that tab's commands, and restoring puts pictures back by index into whatever the order is now.
  • Never open storage while rendering. The first version created the history with createHistory(appRepository()) inside useMemo. In npm run dev, the server renders the studio with ?project= in the address, so that opened IndexedDB on the server and failed ("Switched to client rendering"). The production build prerenders without the query, so the end-to-end tests didn't see it. Now appRepository is passed as a function and only called when a command runs (a history test checks that creating one touches no storage).
  • Deleting several pictures at once works in the command (it takes a list), but selecting several comes in step 12.

Check it

npm test
npm run test:e2e
npm run dev
  • Take five pictures, click the second, press Delete three times: two are left. Ctrl + Z three times: all five are back in the same order, with their thumbnails.
  • Take a picture, press the undo arrow: it goes; redo: it's back. Hover the arrows to see their labels.
  • Undo, then take a new picture: redo is off.
  • Reload: the pictures stay, and undo is off.
