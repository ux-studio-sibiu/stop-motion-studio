Project archive: backup and restore

Each animation on the projects page has a Back up button that downloads it as a .zip. Restore a backup, under New animation, brings one back, on this device or another.

  • A backup holds everything: the photos as taken, the order, how long each picture lasts, its position and look, its objects and drawing, the overlay track, the speed and the safe zone.
  • Restoring makes a new animation, with new ids. It never overwrites one, and restoring twice gives two. Its thumbnails are made anew.
  • A file that isn't a backup, one from a newer studio, or one missing pictures is refused with a note saying why, and nothing is saved.
  • The storage note on the projects page now points to the Back up button, instead of "coming soon".

What was built

  • The archive format, src/core/archive/archive.ts: the stable, public format (version 1). Storage (Dexie) can change behind it.
    • archiveManifest: project.json, the frames in order, each with its picture, and each picture once;
    • readManifest: reads one back, trusting nothing (see Watch out), with new ids;
    • ArchiveError and its messages; ARCHIVE_LIMITS.
  • Storage: importProject in ProjectRepository and the Dexie repository. It saves the project, frames, pictures and thumbnails in one transaction, and fails, saving nothing, if a picture is missing or the project exists. It's in the repository contract (repositoryContract.ts), so every storage is held to it.
  • The zip, src/adapters/archive/projectArchive.ts, with fflate: exportArchive stores the photos as they are (JPEG doesn't shrink further) and compresses the JSON. importArchive unpacks only what a backup holds, opens every picture, and only then saves it all.
  • Thumbnails for restored pictures: decodePicture, src/adapters/images/thumbnail.ts, the same size as capture's.
  • The projects page: the Back up button on each card (ProjectCard), and Restore a backup with a note about what happened (ProjectsPage). The card's buttons now have a row of their own, so the name keeps the card's width. download is shared with the export buttons (useExport.ts).
  • New dependency: fflate 0.8.3 (MIT), pinned exactly.

Decisions

  • Always new ids, not only when the animation exists already. That's simpler and safer: the pictures' ids would collide too, and a restore can then never overwrite anything.
  • All or nothing. Everything is checked and every picture opened before anything is saved, then it's saved in one transaction.
  • The photos as stored, not re-encoded, so a backup loses nothing. Thumbnails aren't in the archive; they're made again on restore.
  • Unknown kinds of object are left out, as the renderer already skips them. A backup from a newer studio is refused outright (its version is higher), rather than read partly.

Watch out

  • Nothing in a backup is trusted. Every value is checked and kept in range: sizes, speed, lengths, positions, looks, safe zone, boxes, and each kind's settings through its own reader. There are caps: 5000 pictures, 200 objects on a picture, 500 overlays, 2000 lines in a drawing, 25 MB a photo, 1.5 GB unpacked.
  • Zip bombs: sizes are checked before anything is unpacked. Only project.json and images/*.jpg are unpacked; anything else in the zip is ignored.
  • Big animations: a backup is made in memory, so a few hundred pictures is a few hundred MB for a moment. That's fine on a computer, tighter on an old tablet.

Check it

  • Make an animation with a held picture, a moved and brightened one, a bubble, a drawing and a title on the overlay track. Back it up, delete it, restore it: everything is back. Open it.
  • Restore it again: there are two.
  • Restore any other .zip: the note says it isn't a backup.

Review checklist

  • a backup brings everything back, as a new animation, never overwriting
  • a bad file is refused with a reason, and nothing is saved
  • nothing in a backup is trusted: values kept in range, kinds known, sizes capped, nothing unpacked beyond the limits
  • the format is plain code in core; storage's importProject is in the contract
  • npm test, npm run test:browser, npm run lint, npm run typecheck, the build and projects.spec pass
