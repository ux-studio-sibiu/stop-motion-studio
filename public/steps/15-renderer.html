Renderer

One function now draws the animation at any moment: renderAt(ctx, scene, images, tick). It finds the picture on screen at that time, fits it into the canvas, and applies its position, turn, size, mirroring and brightness. Playback (16), onion skin (17) and export (25–27) will all draw through it, so what a child sees is what ends up in the video. For now the stage uses it: with the camera off, it shows the selected picture. This step also adds a third kind of test: pixel tests that run in a real browser.

  • e2e/stage.spec.ts (2 tests).

How a picture is placed

size   = containSize(picture, canvas)      fit whole: bars if the shapes differ
matrix = translate(canvas centre + x·W, y·H)
       · rotate(rotation, clockwise)
       · scale(scale × (flipX ? −1 : 1), scale × (flipY ? −1 : 1))
       · translate(−size.width / 2, −size.height / 2)
ctx.setTransform(matrix); ctx.filter = "brightness(…) contrast(…)"
ctx.drawImage(picture, 0, 0, size.width, size.height)

Everything happens around the picture's centre. x and y are fractions of the canvas (step 02), so a picture moved a quarter of the way right stays a quarter of the way right at any resolution.

Decisions

One renderer, any canvas

renderAt takes any 2D context: the stage's canvas, playback's, or an OffscreenCanvas in a worker for export. It is plain TypeScript in core/. It doesn't know where pictures come from: it asks an images(imageId) function and gets a decoded picture or nothing. When the picture isn't decoded yet, it draws the background and returns missing: true, so the caller can decode it and draw again.

A time, not a frame number

It draws "the animation at tick 12", not "frame 3". Speech bubbles (step 23) belong to a frame, but text and shapes on the second layer (step 24) live in time and can span several frames. Drawing by time is what lets both appear in the right place.

The canvas has the project's size

The stage canvas is 1280 × 720 (the project's resolution), and CSS scales it to fit with object-fit: contain. That's already sharper than the stage on most screens, so it doesn't add extra pixels for high-density screens. Export draws at exactly the project's size, so the stage and the file are drawn the same way.

Bitmaps, and closing them

Drawing a JPEG means decoding it first, a few milliseconds each. So each photo is decoded once into an ImageBitmap and reused. A decoded 1280 × 720 photo is about 3.5 MB, held outside the JavaScript heap where the garbage collector doesn't see it. So the cache keeps only the 30 most recently used (about 100 MB at most), and close()s each one it drops, which frees it straight away. Leaving the project clears it, and a decode that finishes after that is closed too.

The stage: live while the camera is on

The plan said "the stage shows the selected frame". But since step 12 a new picture selects itself, so that would replace the live camera with a photo after every capture, and a child needs the live view to set up the next pose. So:

  • Camera on: the stage is live. Onion skin (17) will lay the previous picture over it.
  • Camera off, with pictures: the stage shows the selected picture (or the last one), drawn by the renderer. The camera message becomes a small bar along the bottom: "Turn on the camera to take more pictures".
  • No pictures yet: the big camera message, as before.

Browser mode is still Vitest: the same describe, it and expect, and the test imports the renderer directly. The difference is that the test file runs inside a browser page, so document.createElement("canvas") and getImageData are real. There's no app, no server and no clicking, which is what makes it seconds, not half a minute.

vitest.config.mts defines two projects:

  • unit: Node, every *.test.ts except the browser ones;
  • browser: Chromium, only *.browser.test.ts.

npm test picks the first (--project unit), so it stays Node-only and fast.

Reading pixels

The test source is a synthetic 160 × 90 picture of four solid quadrants: red, green, blue, yellow. A test draws it with a known transform and reads chosen points back with getImageData(x, y, 1, 1).

  • Mirrored: green where the red was.
  • Turned 180°: yellow in the top-left.
  • Half size: black around it.

Solid colours make the expected values exact. The assertion still allows ±2 per channel, because edges are smoothed (anti-aliased) and filters round. The points are chosen away from edges anyway.

To prove the tests catch mistakes, the flip was broken on purpose. The flip test failed with pixel (20, 20) is rgb(255, 0, 0), expected rgb(0, 255, 0), and passed again once the flip was restored.

Watch out

  • Canvas filters in Safari. Brightness and contrast use ctx.filter. Older Safari versions ignore it, so pictures would draw unadjusted there. Step 19 (brightness) must check Safari, and fall back to manipulating the pixels if needed.
  • Every bitmap must be closed. Code that takes bitmaps out of the cache must never close them itself, and must not keep them after clear().
  • Pixel tests stay small. Synthetic images and a handful of points each. No photos, no text, no screenshot comparisons, which break with every font or browser update.
