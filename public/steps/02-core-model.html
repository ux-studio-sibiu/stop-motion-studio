Core model

The shape of an animation, written down as plain TypeScript: projects, frames, images and thumbnails, the defaults a new one starts with, and how long each frame stays on screen. No UI changes; everything later builds on these types, and they come with tests.

What was built

  • src/core/model/types.ts: Project, Frame, Transform, Adjust, StoredImage, StoredThumb.
  • src/core/model/ids.ts: newId(), a wrapper around crypto.randomUUID().
  • src/core/model/project.ts: createProject(), createFrame(), frameDuration(), projectDuration(), clampFps(), clampHold(), and the constants: SCHEMA_VERSION, default and maximum resolution, fps limits, FPS_OPTIONS, frozen DEFAULT_TRANSFORM / DEFAULT_ADJUST.
  • src/core/model/index.ts: one import path, @/core/model.
  • src/core/model/project.test.ts: 12 tests. The step 00 smoke test and its meta.ts are gone.

src/core/model/types.ts

export type Project = {
  id: string;
  schemaVersion: number;
  name: string;
  width: number;           // working resolution in px; captures are resized to it
  height: number;
  fps: number;             // ticks per second; a frame lasts `hold` ticks
  frameIds: string[];      // the order of the animation
  createdAt: number;
  updatedAt: number;
};

export type Frame = {
  id: string;
  projectId: string;
  imageId: string;         // several frames may share one image (duplicate / hold)
  hold: number;            // whole ticks on screen, >= 1
  transform: Transform;
  adjust: Adjust;
};

How the pieces relate

Project ── frameIds: [f1, f2, f3, f2]      the order (f2 appears twice)
   │
   ├── Frame f1 ── imageId: i1 ──► StoredImage i1 (full photo)
   ├── Frame f2 ── imageId: i2 ──► StoredImage i2   + StoredThumb i2 (160 px)
   └── Frame f3 ── imageId: i2       (a duplicate: same photo, own transform)

Decisions

Plain data, no classes

Everything is a type plus functions that return new objects. Plain objects go into IndexedDB as they are (step 06), into a JSON archive (step 27), and can be copied and compared for undo (step 11). A class would need converting at each of those boundaries.

Order lives in project.frameIds

Frames don't carry an order number. Moving a picture from position 40 to position 2 rewrites one list on one record, instead of renumbering 39 frames, and undoing it puts the old list back. The cost is keeping the list and the frames table in step; the load step in 07 repairs any drift, and projectDuration() already skips ids without a frame.

Time is counted in ticks, not milliseconds

A frame has hold (how many ticks it stays) and the project has fps (ticks per second). frameDuration = hold × 1000 / fps. When a child changes the speed, a picture they "held for three" stays three times as long as the others at every speed. With milliseconds per frame, changing the speed would have to rewrite every frame or break that rhythm.

Since this step, the plan added a time-scaled timeline: a picture's width is its duration, dragging its edge changes hold (snapped to whole ticks, step 13), and a faint seconds ruler shows real time. A second layer of text and shapes (step 24) uses the same ticks for its start and length, so both layers stay lined up when the speed changes. Speech bubbles (step 23) are stored on the frame they belong to. None of these change the types written in this step; they add to them. Also planned: a duplicated frame must look exactly like its source, so step 12 adds a cloneFrame() next to createFrame() that copies every field and is tested field by field.

Transforms are relative to the project

x and y are fractions of the frame's width and height (0.1 = 10% to the right), scale 1 means "fits the frame", rotation is in degrees. If the working resolution changes, moved pictures stay where they were put.

Adjustments are numbers, never pixels

brightness and contrast default to 1 (unchanged) and are applied when drawing (step 20). The original photo is never rewritten, so every change can be undone or reset.

Limits are enforced where objects are made

  • Resolution is capped at 1920×1080 and rounded down to even numbers, because the H.264 encoder in step 26 rejects odd sizes.
  • fps is a whole number from 1 to 30; hold is a whole number of at least 1. NaN falls back to the defaults instead of spreading.
  • A blank name becomes "My animation".

Later steps that change these values (speed control, hold buttons) go through the same clampFps() / clampHold().

UUIDs for every id

crypto.randomUUID() ids are made on the device and never clash, even when a project archive from another computer is imported (step 27). They're wrapped in newId() so tests or a future storage backend can swap the generator in one place.

schemaVersion on every project

Stored data outlives the code that wrote it. Each project records the shape it was saved with, so a later version (layers, sound) knows what to migrate.

Defaults are frozen, frames get copies

DEFAULT_TRANSFORM and DEFAULT_ADJUST are Object.freezed, and createFrame() spreads them into new objects. Without that, editing one frame's transform in place could silently move every new frame.

Watch out

  • Blobs are in the types but not in the store. StoredImage.blob and StoredThumb.blob belong in IndexedDB and short-lived caches. The Zustand store (step 04) holds Project and Frame only.
  • crypto.randomUUID() needs a secure context: localhost or HTTPS. On a tablet opening the dev server by LAN IP over plain http://, newId() throws.
  • Types are compile-time only. Data read back from IndexedDB or an imported archive isn't checked by TypeScript; step 27 validates archives at runtime.
  • The layering rule applies here. Nothing in src/core/model/ may import React, Next, Dexie or Zustand.

Check it

npm test
npm run lint

12 tests pass: defaults, unique ids, name fallback, resolution caps and even sizes, fps and hold clamping, frozen defaults, durations, rhythm kept across speeds, and the total length skipping missing frames.

Try breaking it: in createFrame(), replace { ...DEFAULT_TRANSFORM, ...transform } with plain DEFAULT_TRANSFORM. The "never shares or mutates the default objects" test fails, because every frame would now point at the same object. Undo the change afterwards.
