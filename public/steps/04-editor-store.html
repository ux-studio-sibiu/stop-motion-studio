Editor store

One place for what the studio is showing and doing right now: the open project and its frames, which pictures are selected, whether it's playing and where the playhead is, and the timeline zoom. Components read just the piece they need and re-render only when that piece changes. Photos stay out of it, in a separate image cache.

What was built

  • zustand 5.
  • src/store/editorStore.ts: createEditorStore(), the state type in four slices, and orderedFrames().
  • src/store/useEditor.ts: the app's one store, editorStore, and the hooks useEditor(selector), useEditorShallow(selector) and useOrderedFrames().
  • src/adapters/images/imageCache.ts: createImageCache(), a Map of image id → Blob with put, get, delete, clear.
  • Tests: editorStore.test.ts (17) and imageCache.test.ts (2). 42 tests in total now.
  • The studio loads a fresh, empty project into the store on opening, unloads it on leaving, and its title reads the name from the store. In development, window.editorStore is there to poke at from the browser console.

Decisions

Zustand, and how it works

A Zustand store is an object with getState(), setState() and subscribe(). Actions are ordinary functions inside the state that call set() with the fields that change; Zustand merges them into a new state object and tells subscribers. In React, useStore(store, selector) subscribes the component and runs the selector after every change; the component re-renders only if the selector's result is different (compared with Object.is). There's no provider, no reducer and no action types, which keeps it small, but the "replace, don't edit" rule of Redux still applies.

A vanilla store plus a hook, not one create()

createEditorStore() uses createStore from zustand/vanilla, which has no React in it. That means tests create a fresh store each time and call actions directly, with no rendering, and non-React code (the playback clock in step 16, plugins in step 22) can use the same store. useEditor.ts makes the one instance the app uses and wraps it in hooks.

One module-level store, no React context

There's only ever one studio on screen. A store in a module is simpler to reach than one passed through a context provider, and the factory still allows a second one if that ever changes. Opening a project calls loadProject, which resets selection and playback; leaving calls unloadProject.

Metadata only

The store holds Project and Frame objects: ids, numbers and strings. Photos are Blobs of hundreds of kilobytes each and go into the image cache, keyed by imageId. Keeping them out of the store keeps state copies cheap (every change makes new objects), keeps undo snapshots small (step 11), and means devtools never try to print a photo. The cache is a plain Map for now; step 07 replaces it with IndexedDB behind the same idea.

Frames by id, order in the project

frames is a record keyed by id, and project.frameIds is the order, exactly as stored (step 02). Looking up a frame is instant, and changing one frame doesn't copy the order. orderedFrames() builds the list when a component needs it, skipping ids without a frame.

Selectors keep re-renders small

Each component picks what it needs: the title subscribes to the project name, not to the whole project; the timeline will subscribe to the frame list, the playhead to the playhead. When the playhead moves 60 times a second during playback (step 16), only the playhead line re-renders. A selector that builds a new array (like orderedFrames) would look "changed" every time, so useEditorShallow compares its items instead (useShallow).

The playhead is a tick

The roadmap first said currentIndex. Since then the timeline became time-based, with overlays that span several pictures, so "where are we" is a time in ticks. Which picture is on screen is worked out from it.

Small guard rails in the actions

  • insertFrames clamps the position into the list and does nothing without a project.
  • select drops unknown ids and duplicates.
  • play refuses an empty animation; seek rounds to whole, non-negative ticks.
  • setTimelineZoom stays between 40 and 640 px per second. The zoom is about the screen, not the animation, so loading another project keeps it.

Watch out

  • Never edit state in place. state.project.frameIds.push(id) changes the array without telling Zustand, so nothing re-renders, and undo snapshots silently change. Actions always build new arrays and objects; a test checks that the previous state is untouched after an insert.
  • Selectors that build new objects ((s) => ({ a: s.a, b: s.b }), .map, .filter) must go through useEditorShallow, or the component re-renders on every store change. In React 19 this can also cause an "infinite loop" warning.
  • No MediaStream, DOM nodes or Blobs in the store. The camera stream stays in useCamera, elements in refs.
  • Actions outside rendering. Call editorStore.getState().someAction() in effects and event handlers, never during render.
  • The project isn't saved yet. Every visit to the studio starts a new empty project until step 07; the ?project= id is read but not used for loading.

  • store/ doesn't import from studio/ or app/
