Playback

The animation plays. Press the big Play button (or Enter) and the stage shows it at its speed, over the live camera, while a red playhead runs along the timeline. A picture that lasts three ticks stays three times as long. The speed control goes from slow to fast, Loop starts it again at the end, and dragging along the ruler scrubs through it.

Changed later:
  • Play is a regular button, with a green icon. It keeps the same width when it switches to Pause.
  • Speed and Loop moved into a dropdown on the arrow beside Play (PlaybackBar.tsx, with the open and close logic shared in useDropdown). Loop is now a checkbox there.
  • See-through sits next to Play, with its own dropdown (step 17).

Decisions

Counting from the start time

The clock never adds "one tick" per screen refresh. It works out tick = start + floor(elapsed ms × fps / 1000) from when Play was pressed, so playback keeps the right speed however unevenly the browser draws. Browsers stop drawing in a background tab. When the tab comes back, the clock jumps to where the animation would be by then, instead of racing through everything it missed. The clock is pure maths with now passed in, so its tests use made-up times and nothing waits.

Where it starts, where it stops

  • Play starts at the first selected picture, or at the start if none is selected. The playhead line sits there before you press it.
  • Pause selects the picture it stopped on, so the stage, the timeline and the next Play agree.
  • Reaching the end without Loop goes back to the start for the next Play.
  • Clicking a picture, scrubbing, or taking a picture stops playback.

A snapshot of the frames

Playback plays the frames as they were when Play was pressed. Changing the speed or the loop setting while it plays starts it again from where it is, with the new setting.

Speed is part of the animation, loop isn't

The speed is saved with the animation, because the video will play at it, and changing it is undoable. Everything is counted in ticks, so the whole timeline, ruler included, rescales. Loop is how you watch, so it lives in the store only.

The stage while playing

Playback draws over the live camera; the camera keeps running underneath, so stopping shows the live view again at once. Pictures are decoded a few ahead of the playhead (4). If one still isn't ready, the stage keeps the previous picture rather than flashing black.

A bug the tests found

Ctrl+Z didn't undo while the speed slider had keyboard focus. The undo shortcut skipped every <input>, so a text field's own undo would win. But a slider has no undo of its own. The shortcut now skips only fields you type in.

Watch out

  • Long animations at high speed rely on decoding keeping up (about 5 ms per picture). At 15 pictures per second that's fine. If it stutters, decode further ahead.
  • The speed slider saves one undo step per notch it passes, so dragging from slow to fast makes four.
  • Onion skin (step 17) draws over the camera too; it must hide while playing.

Check it

npm test
npm run test:e2e
  • Take a few pictures, make one longer (step 13), press Play: the long one stays longer, and the red line runs along.
  • Turn Loop off: it stops at the end. Turn it on: it keeps going.
  • Move the speed slider while it plays: it speeds up, and the timeline gets shorter. Ctrl+Z puts the speed back.
  • Drag along the ruler: the stage follows the pointer.
