Build steps · Step 07 of 33 · Part 3 Persistence and testing

Save captures and survive a refresh

Pictures are now saved in the browser as they're taken. Opening the studio creates a project and puts its id in the address; reloading, closing the tab or coming back tomorrow shows the same pictures. Two tabs on the same project stay in sync. A broken order is repaired on load, and an unknown project gets a friendly page instead of an empty studio.

What was built

  • src/core/model/order.ts: repairFrameOrder() and sameOrder(), with 6 tests.
  • ProjectRepository.watchProject(id, onChange): reports the project now and after every change. The Dexie version uses liveQuery. 3 new contract tests.
  • src/adapters/storage/appRepository.ts: appRepository(), the app's repository, made on first use.
  • syncProject() in the store: mirrors a saved change, keeping the selection and playhead when it's the same project. 2 new tests. 72 tests in total.
  • src/studio/useProject.ts: creates, loads and follows the project in ?project=, and returns loading, ready or missing.
  • src/studio/useCapture.ts: a capture is now saved with insertFrames (photo, thumbnail, frame and order in one transaction).
  • src/studio/media.ts: only the thumbnail cache is left, plus loadMissingThumbs(). Full photos stay in IndexedDB.
  • The "This animation isn't here" page for unknown ids.

How a capture travels now

press
  → captureFrame()                     JPEG + thumbnail (step 05)
  → thumbs.put(id, thumb)              into memory first, so the timeline can show it at once
  → repository.insertFrames(...)       one IndexedDB transaction: image, thumb, frame, new order
        │
        ▼  Dexie notices the write (liveQuery), in this tab and in any other open tab
  → watchProject callback              project + all its frames, read fresh
  → repairFrameOrder()                 order matches the frames? (it should)
  → loadMissingThumbs()                another tab's new picture: fetch its thumbnail
  → store.syncProject()                the store mirrors storage
  → Timeline re-renders

Decisions

Storage is the source of truth, the store mirrors it

A capture doesn't add a frame to the store directly. It saves, and the saved result flows back into the store, exactly like a change made in another tab. There's one path for data to reach the screen, so the timeline can't show a picture that failed to save, and nothing extra is needed to keep tabs in sync. The store still owns everything that isn't saved: selection, playhead, zoom. IndexedDB writes take milliseconds, so the round trip isn't visible.

watchProject is on the repository, not a Dexie hook

The roadmap planned to read the timeline with Dexie's useLiveQuery React hook. That would tie components to Dexie. Instead, "tell me when this project changes" became part of ProjectRepository, with contract tests (reports now, reports after each change, reports undefined after a delete, stops when asked). Dexie implements it with liveQuery, which re-runs the query whenever a write touches what it read, and uses a BroadcastChannel to hear writes from other tabs. A cloud repository would implement the same method with its own change feed.

Thumbnails before the store

The thumbnail cache isn't reactive: the timeline reads thumbs.url(id) when it renders. So every update first makes sure all its thumbnails are in memory, and only then updates the store. A capture puts its own thumbnail in before saving; a picture from another tab is fetched with getThumb; opening a project loads all thumbnails at once with listThumbs. If a newer update arrives while thumbnails load, the older one is dropped, so updates never apply out of order.

Repair on load

Frames and the order are always written together, so they should always match. If they ever don't (a crash in an old version, a bad import, a bug), repairFrameOrder drops ids that point at nothing, removes duplicates, and adds frames that aren't in the order at the end. No picture is ever lost from the timeline. The repaired order is saved back, which triggers one more, clean update.

A new project per visit without an id

/studio creates and saves a project, then replaces the address with /studio?project=…. Replace, not push: Back goes to the home page, not to an id-less studio that would create yet another project. A ref guards the creation, so React Strict Mode's double effect in development doesn't make two. Until the projects page (step 09), "Start animating" always starts a new one; the address is how to get back to a project.

Unknown ids get their own page

A project made in another browser, on another computer or deleted can't be shown, and an empty studio would be confusing. The page says so in plain words and offers a new animation.

Full photos aren't kept in memory any more

Step 05 kept every full picture in a memory cache. Now they're in IndexedDB, and nothing on screen needs them yet; playback and export (steps 15-16, 25-26) will read them as needed. Memory per picture is just its 1 KB-ish thumbnail.

Watch out

  • The first update comes after the first render. Until then the store is empty and the title blank for a moment. Capturing is disabled until the project is ready.
  • Each update re-reads all frames of the project. Fine for hundreds of pictures; step 31 measures it with 500.
  • Two tabs can still both edit. Captures from both land safely (each is its own transaction), but later edits (moving, resizing) will be "last write wins". Collaborative editing is out of scope.
  • Saving can fail (storage full). The capture is then dropped with a console warning; step 20 shows a friendly message.
  • The address is the project. Bookmarking it works; sharing it with another computer doesn't (the data is in this browser only).

Check it

npm test
npm run dev
  • Open /studio: the address gets ?project=…. Take three pictures.
  • Reload: the three pictures are back. DevTools > Application > IndexedDB > stop-motion-studio shows one project, three frames, three images, three thumbs.
  • Open the same address in a second tab, take a picture in the first: it appears in the second.
  • Go home and press Back: the same project, not a new one.
  • Open /studio?project=nope: "This animation isn't here".
Checked while building, on the production build with a fake camera: /studio got a project id; two captures saved; after reloading, both thumbnails came back from IndexedDB, and the database held exactly 1 project, 2 frames, 2 images, 2 thumbs; a capture in one tab appeared, with its thumbnail, in a second tab; an order deliberately broken in the database (a ghost id, a duplicate, a missing frame) was repaired on reload and saved back; leaving and coming back with Back showed the same project; an unknown id showed the missing page; no console errors in a fresh tab. Not checked: a real webcam, Safari, the dev server (Strict Mode's double effects).
